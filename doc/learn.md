
# Lab 4 Traps: 门卫、快照与中断的艺术

## 4.1 核心哲学：从“法外之地”到“有法可依”
如果说 Lab 3 是在优化**内存地图**，那么 Lab 4 就是在精雕细琢内核与用户态之间的**国境线**。
● **Trap 的本质**：它是用户态通往内核态的唯一合规通道。无论是系统调用（ecall）、硬件中断（如时钟），还是异常（如除零、页错误），最终都汇聚到 `usertrap()` 这个大关口。
● **硬件协同**：CPU 硬件在 Trap 发生时会自动完成关键动作（如保存 `pc` 到 `sepc`，切换到内核模式，跳转到 `stvec` 指定的地址），这就像是一个自动触发的“紧急避难协议”。

## 4.2 xv6 Trap 机制：保姆级的上下文切换
在实验过程中，我深刻体会到了 xv6 处理 Trap 的严谨性：
1. **快照保存 (Trampoline)**：通过 `uservec`，内核在用户栈还不可信时，借用 `sscratch` 指向的 `trapframe` 紧急保存所有通用寄存器。这就像是在火灾发生瞬间，把所有重要文件（寄存器）扔进保险柜（trapframe）。
2. **身份切换**：切换到内核页表，初始化内核栈指针，最后跳转到 C 语言编写的 `usertrap()`。
3. **分流处理**：`usertrap()` 像个分拣员，根据 `scause` 判断是系统调用、磁盘中断还是时钟滴答。
4. **回滚恢复 (usertrapret)**：处理完后，逆向执行上述流程，通过 `userret` 完美还原用户现场。

## 4.3 闹钟实验 (Alarm) 的实战心得
这次 Alarm 实验是 Trap 机制的深度应用，我踩了几个非常有价值的坑：

### 4.3.1 指针与结构体的“指鹿为马”
在 `sys_sigreturn` 中，最初的代码是：
`myproc()->trapframe = &myproc()->alarm_tf;`
这犯了一个低级但致命的错误：它改变了 `trapframe` 的**指向**。实际上，`trapframe` 应该永远指向那一页特殊的内存映射，正确的做法是**内容拷贝**：
`*myproc()->trapframe = myproc()->alarm_tf;`
这种“偷梁换柱”导致了后续内核访问地址时的 `scause 0xc` (Store page fault)，因为它把指针引向了进程结构体内部，而不是预期的内存页。

### 4.3.2 “防重入”：递归的死循环陷阱
如果处理函数 `periodic` 还没执行完，下一个时钟中断又来了怎么办？
如果不加限制，内核会再次保存 `trapframe`，覆盖掉最初的现场，导致程序再也回不去了。
● **解决之道**：在 `struct proc` 中增加 `alarm_in_handler` 标志位。
● **闭环逻辑**：中断触发时设为 1，拒绝后续触发；直到用户调用 `sigreturn` 系统调用时才重置为 0。

### 4.3.3 细节决定成败：大括号与计数器
一个小小的 `ticks_count` 忘记清零，或者大括号位置放错，都会导致闹钟变成“一次性产品”。在内核这种严丝合缝的机器里，逻辑的一致性比什么都重要。

## 4.4 总结：Trap 是操作系统的心跳
通过 Lab 4，我理解了操作系统是如何在“服务用户”和“保护自己”之间平衡的。Trap 不仅仅是中断，它是内核掌控全局的抓手。只有理解了 Trampoline 页面上的那几行汇编代码，才算真正摸到了操作系统的门槛。
