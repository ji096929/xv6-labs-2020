# LAB3: Page Tables (页表进阶 - 预研与感悟)

## 3.1 架构的质变：从“大通铺”到“单间带户口”
通过预研，我理解了 Lab 3 最大的改动是将全局唯一的 `kernel_pagetable` 演进为每个进程专属的 `p->kpagetable`：
*   **Lab 2 的局限**：所有人共用一张内核地图，导致内核无法在自己的地图里画上每个进程私有的用户地图（否则会冲突）。
*   **Lab 3 的突破**：通过给每个进程发一张“私有内核地图”，内核终于可以把该进程的用户内存映射也偷偷“复印”一份到这张内核地图里。

## 3.2 性能哲学：消灭“软件手动查表”
这是我目前印象最深的一点改进：
*   **手动查表（Lab 2）**：内核像个盲人，拿到用户指针必须通过 `copyin` 这种软件逻辑去查页表，不仅慢，还增加了内核代码的复杂度。
*   **硬件查表（Lab 3）**：由于内核页表里现在有了用户映射，内核代码可以直接解引用用户指针。这本质上是将查表工作甩锅给了 **CPU 硬件 (MMU)** 和 **TLB 缓存**。这种“让硬件干它最擅长的事”的思想是高性能系统设计的基石。

## 3.3 空间换时间的权衡
*   **成本意识**：每个进程多一张内核页表，意味着更多的内存开销（页表本身占内存）。
*   **同步难题**：当全局内核资源（如新挂载了一个磁盘设备）发生变化时，必须同步更新所有进程的私有内核页表。这让我意识到：**世界上没有免费的午餐，极致的性能往往伴随着复杂的管理成本。**

## 3.4 安全与便利的钢丝绳
*   **打破绝对隔离**：在内核页表里映射用户数据，虽然方便了内核，但也增加了一丝风险（内核 Bug 可能会更直接地破坏用户数据）。
*   **设计美感**：学习了 Linux 历史上从“单表共享”到“双表隔离（KPTI）”的演进，再看 xv6 从“极简双表”到“优化版双表”的改进，我深刻体会到：**好的设计不是一蹴而就的，而是在安全与效率的博弈中不断迭代出来的。**

## 3.5 实验具体闭环 (Implementation Steps - 预设)
1.  **私有化**：修改 `struct proc`，增加 `kpagetable` 字段。
2.  **克隆**：在进程创建时，参照 `kernel_pagetable` 初始化私有内核页表。
3.  **桥接**：实现用户映射到私有内核页表的同步逻辑。
4.  **提速**：重写 `copyin` 等函数，尝试利用硬件 MMU 直接访问用户数据。
## 3.6 任务一实战：vmprint 的“显微镜”效应
我实现了 `vmprint` 函数并观察了第一个进程 `init` 的页表，这验证了之前的多项理论：
*   **三级结构的具象化**：打印出的 `.. .. ..` 嵌套层次，完美对应了硬件 Sv39 的三级页表查找流程。每一级索引范围都是 0-511。
*   **内存布局的印证**：
    *   **Page 0 (代码/数据段)**：位于虚拟地址 `0` 附近，具有 `R/X` 权限。
    *   **Page 1 (Guard Page)**：位于代码段上方，你会发现它的有效位虽然是 `V`，但权限位可能是空的，这正是它能捕获“越界”行为的物理基础。
    *   **Page 2 (用户栈)**：紧邻保护页上方，它是用户程序赖以生存的临时数据区。
*   **Trampoline 的孤独守护**：你会发现在页表的极高索引位置（如 `255` 号槽位）有一个孤零零的条目，那就是 `Trampoline`。它距离用户数据区几十个 GB 远，但却在每个进程的页表里都雷打不动地占据着那个最高点。

## 3.7 关于“权限位”的深度反思
在实现过程中，我注意到 `vmprint` 需要判断一个 PTE 是否为“叶子节点”：
*   **核心逻辑**：如果一个 PTE 的 `V` 位有效，但 `R/W/X` 全为 0，说明它还不是真正的物理内存页，而是一把指向“下一级档案柜”的钥匙。
*   **感悟**：这种设计极大地节省了空间。对于进程没用到的地址空间，内核只需要在第一层或第二层标记为无效，就不必为下层分配昂贵的 4KB 物理内存。
