# LAB2: System Calls (系统调用)

## 1. Trace 系统调用实现

### 1.1 核心底层机理：跨越“权力鸿沟”
通过实现 `trace`，我深入理解了系统调用（Syscall）并非简单的函数调用，而是一场硬件与软件的“接力赛”：
*   **语言的地位与栈的本质**：理解了汇编语言拥有“绝对自由”，而 C 语言是“戴着枷锁的舞者”。C 运行的前提是必须有**栈**。在 `_entry` 汇编中设置 `sp` 指寄存器，本质上是在为 C 代码“铺设地基”。没有这几行汇编，C 编译器生成的局部变量和返回地址将无处安放。
*   **ecall 的“门铃”效应**：`ecall` 指令是用户态被允许执行的极少数特权触发器。它不带目标地址，防止了用户程序随意跳转到内核禁区。它像一个“固定按钮”，按下后硬件会强制切换 CPU 到 **Supervisor Mode**，并强行将程序计数器（PC）拉到内核预设的陷阱入口（`stvec`）。
*   **Trapframe 的“快照”意义**：深刻理解了为什么 `sys_trace` 这种内核函数不能直接读硬件 `a0` 寄存器。因为在进入 C 语言环境后，内核编译器也会使用这些寄存器。为了保证数据不丢失，内核必须在汇编阶段（`trampoline.S`）将用户当时的寄存器状态“复印”到该进程的 `trapframe` 备份区。`argint` 函数的本质就是从这个“档案袋快照”中打捞用户参数。

### 1.2 启动自举与权限演变
通过阅读文档与 GDB 调试，我还原了计算机从“白纸”到“世界”的过程：
*   **权限降级的艺术**：学习了 `start()` 函数如何利用 `mret` 指令“金蝉脱壳”。通过手动伪造 `mstatus` 和 `mepc` 寄存器，诱骗硬件认为自己是在从一次中断中“返回”，从而实现从最高权力的 **Machine Mode** 优雅降级到 **Supervisor Mode**。
*   **第一个进程的“脚手架”作用**：理解了为什么不直接运行 `/init`。内核通过手动捏造一个极简的 `initcode.S`（种子进程），目的是为了复用标准的 `exec` 系统调用流程。这样内核就不需要为第一个进程写特殊的加载逻辑，维持了系统设计的优雅一致性。

### 1.3 内存与隔离的哲学
*   **每个进程独立的内核栈**：这是实现“进程在内核态睡觉”的关键。如果公用内核栈，一旦进程 A 在内核等待 IO 被挂起，进程 B 进来就会覆盖 A 的执行现场。每个进程配备专属内核栈，确保了它们即便在内核办公室里干活，也互不干扰。
*   **虚拟地址的幻觉**：xv6 利用 RISC-V 的 SV39 页表，为每个进程编织了一个“我拥有整个物理内存”的幻觉（地址从 0 开始）。这种抽象不仅简化了编程，更在硬件层面实现了进程间的物理隔离。

### 1.4 工程实践与调试心得
*   **GDB 的上帝视角**：学会了利用 `make qemu-gdb` 在 PC 为 `0x1000`（Boot ROM）或 `0x80000000`（内核入口）时进行拦截。这种观察能力是理解黑盒系统最有效的手段。
*   **环境适配的韧性**：解决了 Python 3.13 移除 `pipes` 库导致的评测脚本崩溃，以及 QEMU 版本过高导致的黑屏问题。意识到作为底层开发者，必须具备修改工具链源码（如 `gradelib.py`）和优化 IDE 索引（如配置 `clangd`）的能力。

### 1.5 实验具体闭环 (Implementation Steps)
1.  **扩展 PCB**：在 `struct proc` 中新增 `trace_mask` 字段。
2.  **存根接入**：通过 `usys.pl` 自动生成汇编 Stub，并在 `kernel/syscall.h` 中定义静态编号。
3.  **内核逻辑**：在 `sysproc.c` 中实现 `sys_trace()`，修改当前进程的掩码。
4.  **进程继承**：在 `fork()` 中完成 `trace_mask` 的拷贝，确保调试能力的延续性。
5.  **拦截分发**：在 `kernel/syscall.c` 的 `syscall()` 入口处，利用位运算 `(1 << num) & p->trace_mask` 实现对所有系统调用的集中监控与打印。
